pytest로 유닛 테스트 짜기

레슨 14에서 notes.py를 id 기준으로 리팩터링하면서 버그를 세 번 만났다(학습 기록 0016) — 그중 하나는 에러 없이 조용히 실패해서 눈으로 봐도 잘못된 걸 알아채기 어려웠다. 유닛 테스트(unit test)는 "이 함수가 이런 입력을 받으면 이런 결과를 내야 한다"를 코드로 적어두고, 코드를 고칠 때마다 자동으로 다시 확인하는 방법이다. pytest는 파이썬에서 이 유닛 테스트를 짜고 돌리는 가장 널리 쓰이는 도구다.

새 문법 하나: assert. assert 조건은 조건이 참이면 아무 일도 안 일어나고, 거짓이면 AssertionError를 낸다. 테스트는 결국 "이 값이 내가 기대한 값과 같은지"를 assert로 확인하는 함수들의 모음이다.

핵심 개념 1 — assert

>>> assert 1 + 1 == 2
>>> assert 1 + 1 == 3
Traceback (most recent call last):
  ...
AssertionError

if와 비슷해 보이지만 목적이 다르다 — if는 "다른 분기로 흘러가라"는 뜻이고, assert는 "이게 거짓이면 여기서 뭔가 잘못된 거니 바로 멈춰라"는 뜻이다.

핵심 개념 2 — 테스트 함수의 모양

pytest는 규칙을 따르는 파일과 함수를 자동으로 찾아 실행한다: 파일 이름이 test_로 시작하고, 그 안의 함수 이름도 test_로 시작하면 pytest가 알아서 찾아 실행하고, 안에서 assert가 전부 참이면 통과(초록), 하나라도 거짓이면 실패(빨강)로 표시한다. 

# test_notes.py
from notes import next_id

def test_next_id_empty_list():
    assert next_id([]) == 1

def test_next_id_with_existing_notes():
    notes = [{"id": 1, "title": "a", "content": "x"}]
    assert next_id(notes) == 2

핵심 개념 3 — fixture로 준비 코드 중복 없애기

테스트가 늘어나면 notes = [{"id": 1, "title": "a", "content": "x"}]처럼 여러 테스트가 똑같은 준비 코드를 반복하게 된다. @pytest.fixture를 붙인 함수는 테스트 함수의 매개변수 이름과 fixture 함수 이름이 같으면 pytest가 자동으로 실행해서 그 결과를 넣어준다. 

import pytest

@pytest.fixture
def sample_notes():
    return [{"id": 1, "title": "a", "content": "x"}]

def test_next_id_with_existing_notes(sample_notes):
    assert next_id(sample_notes) == 2

def test_find_note_by_id_existing(sample_notes):
    assert find_note_by_id(sample_notes, 1) == {"id": 1, "title": "a", "content": "x"}

매개변수로 sample_notes를 받지 않는 테스트(예: test_next_id_empty_list)는 그대로 두면 된다 — fixture는 필요한 테스트만 골라서 쓰는 것이지, 모든 테스트에 강제되지 않는다.

Primary source pytest 공식 문서 — Get Started — 설치, 첫 테스트 작성, 실행까지 공식 안내로 다시 확인해봐. fixture는 How to use fixtures 문서 참고.

확인 퀴즈

1. assert 1 == 2를 실행하면?
2. pytest가 테스트 함수로 인식하려면 파일과 함수 이름이 어때야 하나?
3. 유닛 테스트를 짜는 핵심 이유는?
4. fixture 함수가 테스트에 값을 넘겨주려면?

직접 해보기

가상환경(레슨 12)을 켠 상태에서 진행한다:

  1. pip install pytest로 설치한다
  2. test_notes.py 파일을 새로 만들고, next_id에 대한 테스트 두 개를 위 예시처럼 작성한다 (빈 리스트일 때 1, 기존 노트가 있을 때 max+1)
  3. 터미널에서 pytest를 실행해서 초록색으로 통과하는지 확인한다
  4. find_note_by_id에 대한 테스트를 두 개 더 추가한다 — 있는 id를 찾는 경우와, 없는 id를 찾는 경우(None을 돌려줘야 한다). 반환값이 dict인지 list인지는 레슨 14에서 겪은 버그의 원인이었으니, 정확히 뭘 기대하는지 먼저 생각하고 assert를 적는다
  5. 일부러 notes.py의 next_id를 살짝 망가뜨려보고(예: max(ids) + 1을 max(ids)로) pytest를 다시 돌려서 빨간 실패가 뜨는 걸 확인한 뒤, 원래대로 되돌린다 — 테스트가 실제로 버그를 잡아낸다는 걸 눈으로 보는 게 목적이다
  6. 지금 test_notes.py에서 notes = [{"id": 1, "title": "a", "content": "x"}]를 반복해서 쓰고 있는 테스트들을 찾아, @pytest.fixture로 sample_notes를 만들어 매개변수로 받도록 고친다. 고친 뒤 pytest를 다시 돌려서 여전히 다 통과하는지 확인한다 — 리팩터링(레슨 14에서 한 것과 같은 개념)이 테스트 결과를 바꾸면 안 된다

막히면 정답을 바로 묻기보다, "지금 뭐가 안 되는지"와 "왜 그런 것 같은지"부터 말해보자. 그게 이 폴더의 핵심 학습 목표(에러 읽는 법)다.
