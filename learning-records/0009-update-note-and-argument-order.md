# 레슨 8: update_note 만들기 — 위치 인자 순서 혼동, 검증 순서 재배치

`update_note(notes, title, new_content)`를 만드는 과정에서 두 가지 막힘이 있었다.

1. **`if n = find_note(...):`** — 대입(`=`)을 조건 자리에 그대로 쓰려다 `SyntaxError`를 만났다.
   에러 메시지가 `'=='` 또는 `':='`를 제안해준 걸 같이 읽고, "대입은 조건이 아니다"라는 걸
   확인한 뒤 레슨 7 패턴(`n = find_note(...)` 다음 줄에 `if n is None:`)으로 스스로 고쳤다.

2. **위치 인자 순서 혼동** — `update_note(title, content, content)`처럼 호출해서
   `TypeError: string indices must be integers, not 'str'`을 만났다. `notes`(전체 리스트)와
   `note`(딕셔너리 하나)를 같은 것으로 헷갈려 했다. `add_note(notes, title, content)` 호출과
   나란히 비교해서 "함수 인자는 이름이 아니라 위치로 짝지어진다"는 걸 설명한 뒤에야
   첫 번째 자리에 `notes`를 넣어야 한다는 걸 이해했다.

3. **검증 순서 문제** (학습자가 먼저 발견) — 처음 짠 코드는 제목이 있는지 확인하기도 전에
   무조건 새 내용을 먼저 `input()`으로 받고 있었다. "왜 없는 제목인데 내용까지 입력하고 나서
   경고가 뜨냐"고 스스로 문제를 제기했고, `choice == "2"`(찾기)의 순서를 참고해서
   `find_note`로 먼저 확인 → 있을 때만 새 내용을 물어보는 구조로 직접 재배치했다.

**Implications**: "함수 정의의 매개변수 이름"과 "호출할 때 넘기는 값의 순서"가 다른 개념이라는 걸
아직 완전히 체화하지 못했다 — 다음에 인자를 여러 개 받는 함수를 호출할 때 다시 헷갈리면,
`add_note` 호출과 나란히 비교하는 방식이 잘 통했으니 같은 방식을 다시 써볼 것.
반면 "사용자 입력 순서가 UX에 미치는 영향"(불필요한 입력을 먼저 받지 않기)은 스스로 알아챈
지점이라, 검증/입력의 순서를 설계할 때 이 감각을 이미 갖고 있다고 보고 다음부터는 굳이
짚어주지 않아도 될 것 같다.
